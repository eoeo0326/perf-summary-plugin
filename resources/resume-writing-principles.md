# 이력서 작성 공통 원칙

이 문서는 성과 보고서의 이력서 추천·연간 핵심 성취와 실제 이력서의 내용 선정·작성에 적용하는 정본이다. PR 목록의 집계·상태·출처 기록은 별도의 보고서 지침을 따른다.

배포본의 `references/resume-writing-principles.md`와 `resources/resume-writing-principles.md`는 `npm run build:skill`로 생성한다. 사본을 직접 편집하지 않는다. 두 스킬을 같은 버전으로 업데이트하면 동일 원칙을 사용한다.

## 원칙

| 원칙 | 적용할 내용 |
|---|---|
| 처음 읽는 사람 기준 | 서비스·문제·담당 범위를 이해할 수 있게 설명하고, 구현 명칭은 해결 방법을 설명할 때 사용한다. |
| 문제와 기여 중심 | 무엇을 만들었는지와 함께 왜 필요했는지, 본인이 무엇을 바꿨는지, 확인된 결과를 서술한다. |
| 한 항목에 한 성취 | 서로 다른 장애·기능을 쉼표로 묶지 않는다. 같은 문제를 해결한 여러 PR은 하나의 사례로 통합한다. |
| 내부 용어 해소 | 사내 약어·클래스명은 기능 설명으로 대체한다. 필요한 도메인 용어는 첫 등장에 의미·목적을 설명한다. 약어의 영문 전체 이름만 풀어 쓰는 것으로 설명을 대신하지 않는다. |
| 수치의 선택적 사용 | 수치가 없으면 구현 후 가능해진 동작이나 해결한 문제를 제시한다. 라인 수·PR 수로 성과를 대신하지 않는다. |
| 측정 조건 보존 | 측정 대상·환경·비교 조건·적용 범위를 유지한다. 특정 테스트 결과를 일반적인 성능 개선으로 확대하지 않는다. |
| 완료 상태 구분 | 미병합·취소 작업을 완료 성과로 쓰지 않는다. 병합됐더라도 출시·운영 검증 완료로 간주하지 않는다. 진행 중인 경험은 상태를 명시해 완료 성과와 구분한다. |
| 기여 범위 구분 | 팀의 결과, 본인의 분석·구현·검증, 외부 조사 수치를 구분한다. 근거 없이 단독 성과나 제품 전체 개발로 확대하지 않는다. |
| 중요도에 따른 선정 | 문제의 영향, 본인 기여, 결과, 근거의 명확성을 기준으로 선택한다. 공고가 있으면 직무 관련성도 반영한다. |
| 자연스러운 한국어 | 추상 명사·가운데점 나열을 줄이고 구체적인 동작으로 설명한다. 모든 문장에 같은 서술 형식을 강제하지 않는다. |

## 선정·검증·압축

- 문장을 쓰기 전에 후보의 문제, 본인 행동, 결과, 완료 상태, 측정 조건, 출처를 대조한다. 같은 PR의 월별·연간 중복은 PR URL로 통합한다. PR 작성자라는 사실만으로 구현 전체의 단독 담당이나 리딩을 추정하지 않는다.
- 릴리즈 머지·버전 변경·단순 정비를 항목 수를 채우기 위한 성과로 만들지 않는다. 활동량은 통계에 남기고 성과의 중요도와 구분한다. 수치가 없어도 구체적인 문제 해결은 추천할 수 있다.
- 근거가 축약됐거나 상태·의미가 상충하면 대표 사례에 필요한 원문·제공 자료를 확인한다. 확인할 수 없으면 수치·평가를 덜고 확인된 구현 범위만 쓰거나 추천을 보류한다. 모르는 의미를 자연스럽게 보이도록 추측해서 고치지 않는다.
- 사용자 확인은 PR 원문 확인과 구분해 기록한다. 의미에 영향을 주는 질문은 별도로 정리하되 확인된 내용으로 완성할 수 있는 초안은 마무리한다.
- 압축할 때는 내부 이름, 부수 기술, 중복 배경, 부수 작업부터 덜어낸다. 문제·본인 기여·확인 결과·필수 측정 조건은 남긴다. 요약과 상세에서 같은 사례를 길게 반복하지 않는다.
- 전체 구조·페이지 수·사례 개수·실무와 개인 프로젝트의 분류는 고정하지 않는다. 자료의 강도, 독자, 공고, 사용자의 분량·비중 선호에 맞춘다. AI 경험도 도구 사용 목록보다 직접 구현·검증·재사용한 절차로 설명한다.

## 문장 예시

아래는 가상 사례이며 실제 사용자 성과의 근거가 아니다.

| 피할 표현 | 개선 예시와 확인할 점 |
|---|---|
| 인증 계층 고도화 — PR 8건 | 토큰 갱신 요청이 서로 기다려 통신이 멈추는 문제를 분석하고, 갱신 전용 통신 경로로 분리해 해결했습니다. 수치가 없어도 문제·행동·결과가 구체적이다. |
| 캐시로 빌드 성능 대폭 향상 | 테스트 러너와 병렬화·캐시 설정을 함께 바꾼 비교에서 빌드 시간이 줄었습니다. 수치가 있다면 환경·측정 대상을 함께 쓰고 한 설정의 효과로 단정하지 않는다. |
| 새 코어 재시도 적용 | 시작 제한 시간을 넘으면 기존 카메라 객체를 해제하고 새 객체로 다시 시도하도록 구현했습니다. 제한 시간·총 시도 수와 최초 시도 포함 여부는 원문에서 확인한다. |
| 모듈 전환·배포 완료 | 구현 PR만 병합되고 앱 적용 PR이 취소됐다면 라이브러리 구현까지만 쓴다. 적용·출시 완료로 확대하지 않는다. |

## 최종 검토

각 성과를 읽고 제품을 미리 모르는 사람도 문제·담당 행동·결과를 이해할 수 있는지 확인한다. 수치의 단위·조건, 완료 상태, 기여 범위가 원문과 일치하고 내부 용어·중복·근거 없는 평가가 남지 않아야 한다. 근거표·확인 메모는 실제 이력서 본문과 분리한다.
